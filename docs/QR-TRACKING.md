# QR-коды и отслеживание источников

Короткие ссылки вида `sintara.io/qr1` для печати: визитки, презентации, флаеры,
стенды. Каждый код — отдельная метка, по которой видно, сколько людей пришло
именно с неё.

## Что нужно сделать один раз после деплоя

1. Netlify → Site configuration → Environment variables → добавить:

   ```
   QR_STATS_TOKEN = 8Z8I8XP4wyWSLs_9FLA8ATBuHxuLG-dr
   ```

   (можно любую другую длинную случайную строку — это пароль от страницы со
   статистикой). Пока переменной нет, страница статистики отвечает 404.

2. Открыть отчёт и сохранить ссылку в закладки:

   ```
   https://sintara.io/api/qr-stats?token=8Z8I8XP4wyWSLs_9FLA8ATBuHxuLG-dr
   ```

3. Отсканировать `qr1` телефоном и обновить отчёт — скан должен появиться сразу.

## Как это работает

1. Человек сканирует QR → попадает на `sintara.io/qr1`.
2. Запрос уходит в функцию `netlify/functions/qr.mjs`. Она **записывает скан** и
   только потом отвечает редиректом 302 на нужную страницу, дописывая UTM-метки:
   `sintara.io/?utm_source=qr&utm_medium=card&utm_campaign=qr1&utm_content=visitka-ivan`
3. GA4 в браузере видит эти метки и записывает сеанс как «источник/канал =
   qr / card, кампания = qr1», плюс отдельное событие `qr_scan`.

Получается два слоя, и они отвечают на разные вопросы:

| | Где смотреть | Что показывает |
|---|---|---|
| **Сканы** | `/api/qr-stats` | Сколько раз бумагу реально отсканировали. Считается на сервере, до загрузки страницы. |
| **Поведение** | GA4 | Что люди делали дальше: сколько страниц, дошли ли до контактов, отправили ли бриф. |

Разница между ними — тоже полезная цифра: 40 сканов и 12 сеансов в GA4 означает,
что две трети закрыли сайт на загрузке. Это повод посмотреть на скорость или на
то, куда ведёт код.

Почему код короткий, а UTM дописываются на сервере: **напечатанную бумагу уже не
переделать, а ссылку — можно**. Куда ведёт `qr1`, меняется одной строкой в
реестре; визитка в кошельке у клиента продолжает работать.

## Текущие коды

| Код | Куда ведёт | Где используется |
|-----|-----------|------------------|
| `qr1` | `/` | Визитка Ивана |
| `qr2` | `/work` | Презентация / КП — последний слайд |
| `qr3` | `/contact` | Стенд / бейдж на мероприятии |
| `qr4` | `/services` | Флаер / буклет по услугам |
| `qr5` | `/en` | Визитка для англоязычных |

Актуальный список всегда в `src/data/qrCodes.mjs` — эта таблица может отстать,
файл нет.

Если отсканируют код, которого нет в реестре (опечатка, старый тираж), человек
попадёт на главную, а не на 404. Такие сканы видны в отчёте отдельной строкой с
пометкой «не в реестре».

## Картинки для печати

```bash
npm run qr
```

Кладёт в папку `qr/` по четыре файла на код, **все с прозрачным фоном**:

- `qr1.svg` / `qr1.png` — чёрный код, для светлых поверхностей;
- `qr1-white.svg` / `qr1-white.png` — белый код, для тёмных;
- плюс `index.html` — контрольный лист: все коды на белом и на чёрном.

SVG — вектор, это отправлять в типографию; PNG — 1024px, для слайдов, сторис и
мессенджеров.

Прозрачный фон — это удобство вёрстки, а не разрешение класть код на фотографию:
сканеру нужен контраст с тем, что просвечивает, и пустое поле вокруг. Держите под
кодом ровную заливку — просто теперь это может быть цвет самой визитки, а не
белая заплатка. Инвертированный (белый) код современные телефоны читают нормально,
но только при реальном контрасте — не кладите его на средне-серый.

**Перед печатью тиража откройте `qr/index.html` и отсканируйте каждый код
телефоном.** Две минуты проверки против тысячи визиток с опечаткой.

Коды сделаны с максимальным уровнем коррекции ошибок (H, 30%): работают
поцарапанными, под углом и при плохом свете. Строго чёрное на белом — сканеру
важен только контраст. Минимальный размер на печати — 2×2 см, вокруг оставить
пустое поле шириной с четыре «клетки» кода.

## Отчёт по сканам

`https://sintara.io/api/qr-stats?token=…`

По каждому коду: всего сканов, уникальных людей, сегодня, 7 и 30 дней, страны и
сетка по дням за две недели. `&format=json` — те же числа в JSON, если
понадобится куда-то выгрузить.

Что учтено в цифрах:

- **Боты и предпросмотры ссылок не считаются.** Кинули `sintara.io/qr1` в
  WhatsApp — его краулер сразу дёргает ссылку; без фильтра это выглядело бы как
  скан. Отсекаются также прелоады браузера.
- **«Людей» — это уникальные посетители по дням.** IP не хранится: из него,
  User-Agent и даты считается хеш, который завтра будет другим. Поэтому один
  человек, сканировавший в понедельник и во вторник, — это 2. Так задумано:
  вопрос «сколько разных людей подошло сегодня», а не слежка за конкретным
  человеком. Заодно это то, что позволяет обходиться без баннера о cookie.
- **Дни — по времени Пхукета (UTC+7)**, а не UTC. Иначе утренние сканы падали бы
  во вчерашний день.
- Хранилище — Netlify Blobs, привязано к сайту. Отдельная запись на каждый скан:
  ничего не теряется, если два человека сканируют одновременно.

Что этот отчёт **не** покажет: что человек делал после перехода. Это в GA4.

## Где смотреть в GA4

Свойство: `G-94EHPVYB44`.

**Реальное время** — «Отчёты → Реальное время», сеанс появляется в течение минуты.

**Через сутки** — «Отчёты → Привлечение → Привлечение трафика», измерение
**«Источник/канал сеанса»**: строки `qr / card`, `qr / flyer`. Для конкретного
кода — измерение **«Кампания сеанса»**: `qr1`, `qr2`, …

**События** — «Отчёты → Вовлечение → События» → `qr_scan`.

Один раз стоит настроить:

1. **Пользовательские параметры.** «Администратор → Специальные определения →
   Создать специальный параметр»: `qr_code`, `qr_medium`, `qr_placement` (область
   действия — «Событие»). Без этого параметры собираются, но в отчётах их не
   выбрать, и задним числом данных не будет.
2. **Ключевое событие.** «Администратор → События» → включить «Отметить как
   ключевое событие» у `qr_scan`, если нужны конверсии.

## Как добавить новый код

1. Дописать запись в `src/data/qrCodes.mjs` — следующий свободный номер.
2. `npm run qr` → картинка появится в `qr/`.
3. Закоммитить и задеплоить: правила маршрутизации генерируются при сборке
   (`scripts/qr-redirects.mjs` → `dist/_redirects`).
4. Проверить на живом сайте: `sintara.io/qr6` должен открыть нужную страницу, а
   скан — появиться в отчёте.

Правила: не переиспользовать и не удалять номер, который уже напечатан — номер
это единственная связь между бумагой и отчётом. Отработавший код лучше просто
перенаправить на главную.

Ещё: **ни одна страница сайта не должна начинаться с `qr`** — всё, что подходит
под `/qr*`, перехватывается счётчиком. Поэтому сам отчёт живёт на
`/api/qr-stats`, а не на `/qr-stats`.

## Если что-то сломается

Редирект устроен так, что человек попадёт на сайт при любой поломке счётчика:
запись в хранилище обёрнута в try/catch и ограничена 1.5 секундами, после чего
302 отдаётся в любом случае. То есть худший сценарий — «сканы не посчитались», а
не «QR-код не работает».

Логи функции: Netlify → Logs → Functions → `qr`.
